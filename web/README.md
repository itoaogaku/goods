# 在庫・販売管理ダッシュボード

**アスリートキャリアセンター**（水上村・町田寮の在庫）と、**陸上部**（アスリートキャリアセンターから仕入れて販売・購買会卸し・プレゼントする在庫）を、別々のNotionデータベース・別々のタブで管理するNext.js製ダッシュボードです。API（Route Handlers）とフロントエンドが1つのNext.jsアプリにまとまっており、Vercelへそのままデプロイできます。

Wix注文データは、初回の過去分一括移行のみ `../migration` のCLIツールを使用し、それ以降は**このアプリが自動的に**新しい注文をNotionへ取り込み続けます（後述「Wix注文の自動取り込み」）。在庫登録・拠点間移動・手入力販売（町田寮・関係者価格・プレゼント・卸し・棚卸調整）はダッシュボード上のフォームから行います。

## 在庫・販売管理の仕組み

### 台帳（ledger）の分離

| 台帳 | タブ | 内容 | Notionデータベース |
| --- | --- | --- | --- |
| `acc` | `/`（アスリートキャリアセンター） | 水上村・町田寮の在庫と販売 | `NOTION_DATABASE_ID` |
| `trackteam` | `/track-team`（陸上部） | 陸上部の在庫と販売（ACCからの仕入れ・個人への販売・購買会への卸し・プレゼント） | `TRACK_TEAM_NOTION_DATABASE_ID` |

2つの台帳は完全に独立したNotionデータベースです。「ACCが陸上部に卸した」場合、ACC側では`卸し`の出庫として記録し、陸上部側では受け取った数量を`入庫`として**別途手入力**します（既存の運用に合わせ、自動連携はしていません）。同様に、陸上部が購買会へ卸す取引も陸上部台帳側に`卸し`として記録します（購買会はACCの在庫拠点ではなく、陸上部の卸し先という位置づけです）。

### 1つのデータベースで表現する取引の種類（`種別`）

どちらの台帳も同じスキーマを使い、`種別`で取引の意味を区別します。

| 種別 | 在庫への影響 | 用途 |
| --- | --- | --- |
| 発注 | **影響なし** | 発注数量・仕入単価を記録（仕入先・納品予定日は必須項目にしていません。必要なら備考欄へ）。発注一覧から納品登録すると、自動的に「入庫」が作成されて在庫に反映されます |
| 入庫 | 該当拠点の在庫が **+数量** | 商品完成時の在庫登録。拠点ごとに数量を入力すると、入力した拠点の数だけ行が作成されます |
| 通常販売 | 該当拠点の在庫が **−数量** | Wix経由の販売（水上村）、および定価での手入力販売 |
| 関係者価格販売 | 該当拠点の在庫が **−数量** | 割引価格での販売 |
| プレゼント | 該当拠点の在庫が **−数量** | 無償譲渡（売上0円でも在庫は減ります） |
| 拠点間移動 | 移動元 **−数量** / 移動先 **+数量** | 水上村⇔町田寮などの在庫移動（1回の移動で1行） |
| 卸し | 該当拠点の在庫が **−数量** | 他者への卸し（ACC→陸上部、陸上部→購買会など）。卸し先は備考欄に記入 |
| 棚卸調整 | 該当拠点の在庫が **数量の分だけ増減**（符号あり） | 棚卸で発見したズレの補正。減らす場合はマイナスを入力 |
| 送料 | **影響なし** | Wix同期が注文ごとの送料を自動登録（商品名「送料」・数量1件として1行）。手入力はできません |

「現在庫」は、各台帳の**全期間**のイベントからこのルールで積み上げて計算します（月別売上などのKPIは `SALES_DATA_SINCE` 以降のみを対象にしますが、在庫残高は開始日に関わらず全履歴を対象とします）。

> **既知の制約**: 現在庫・売上サマリー・未発送一覧・発注一覧は、いずれも呼び出しのたびにNotionデータベースを全件（該当する範囲）読み直して集計しています。データ件数が数千件を超えてくると読み込みに時間がかかるため、該当するAPI（`summary`/`stock`/`pending-shipments`/`purchase-orders`）には`maxDuration = 60`を設定して既定より長く実行できるようにしていますが、データがさらに増えた場合はこれでも不足する可能性があります（その場合はエラーバナーが表示されます。再読み込みで直ることもあります）。将来的にはNotion側にキャッシュを持つ、集計を差分更新にするなどの改善が必要になるかもしれません。

### 発送管理（ステータス）

`ステータス`（未発送/発送済/キャンセル/返金）は、**Wix経由の注文についてはWixのfulfillmentStatus（発送状況）をそのままAPI経由で取り込みます**。Wix上で発送済みにマークすると、次回の同期（自動なら最大1日後、急ぐ場合は手動同期ボタンで即座に）でこのアプリ側のステータスも自動的に更新されます。キャンセル・返金はWixの決済ステータスから判定し、発送状況より優先されます。

- 各台帳のダッシュボード上部に「**発送管理**」パネルがあり、未発送の注文だけが一覧表示されます
- Wix経由でない取引（町田寮の手入力販売・関係者価格販売・プレゼント・卸しなど）や、過去分の手直しをしたい場合のために、パネルおよび下部の「取引・在庫履歴」テーブルの行からその場でステータスを変更することもできます。ただし**Wix経由の注文でこの手動変更を行っても、次回のWix同期でWix側の状態に上書きされる**点に注意してください（Wixが正となる設計です）
- KPIの「未対応注文数」もこのステータスに連動します

## Notionデータベースのスキーマ（両台帳共通）

| プロパティ名 | 型 | 説明 |
| --- | --- | --- |
| 取引ID | タイトル | 取引を一意に表すID（Wix注文番号 or 画面操作時に自動生成） |
| 明細ID | テキスト | 重複登録防止用の一意キー |
| 種別 | セレクト | 発注 / 入庫 / 通常販売 / 関係者価格販売 / プレゼント / 拠点間移動 / 卸し / 棚卸調整 / 送料 |
| 日時 | 日付 | 取引発生日時（発注は発注日） |
| 拠点 | セレクト | ACC台帳: 水上村 / 町田寮　陸上部台帳: 陸上部（発注では納品予定拠点） |
| 移動先拠点 | セレクト | 拠点間移動のときのみ使用 |
| 商品名 | テキスト | 商品名 |
| 数量 | 数値 | 発注では発注数量 |
| 単価 | 数値 | 発注では仕入単価 |
| 合計金額 | 数値 | 数量 × 単価（画面側で自動計算） |
| 備考 | テキスト | 卸し先・贈呈先などの自由記述 |
| 顧客名 | テキスト | Wix同期のみ自動入力（注文者名）。手入力では空欄のまま |
| ステータス | セレクト | 未発送 / 発送済 / キャンセル / 返金 |
| 発注ステータス | セレクト | 発注済み / 一部納品 / 納品完了 / キャンセル（発注のみ使用） |
| 受領済み数量 | 数値 | 発注のみ使用。納品登録のたびに自動加算されます |

`../migration/README.md` に記載の旧スキーマ（`注文ID`/`販売日時`のみ）から移行する場合は、Notion側で以下を行ってください。

1. `注文ID` → `取引ID`、`販売日時` → `日時` にプロパティ名を変更（型・データはそのまま）
2. `種別`（セレクト）・`拠点`（セレクト）・`移動先拠点`（セレクト）・`備考`（テキスト）・`発注ステータス`（セレクト）・`受領済み数量`（数値）を追加
3. `cd ../migration && npm run migrate -- backfill` を実行し、既存行に `種別=通常販売` / `拠点=水上村` を一括補完

### 陸上部用データベースの作成

1. ACCのデータベースを複製する（または同じプロパティ構成で新規作成し、`拠点`の選択肢を `陸上部` のみにする）
2. 同じNotion Integrationを「コネクト」する
3. データベースIDを `TRACK_TEAM_NOTION_DATABASE_ID` に設定

## Wix注文の自動取り込み

ACC台帳（水上村）には、Wixの新しい注文が自動的に反映されます。

- **定期同期（Vercel Cron）**: `vercel.json` の設定により、`/api/acc/sync-wix` が既定で **1日1回（毎日UTC 21:00 = 日本時間 6:00）**に自動実行され、Wix eコマース REST API（Orders Search）から `WIX_SYNC_SINCE`（未設定時は `SALES_DATA_SINCE`）以降の注文を取得します。Notion未登録の明細は `種別=通常販売` / `拠点=水上村` として新規追加し、**ステータス（未発送/発送済/キャンセル/返金）はWixのfulfillmentStatus・paymentStatusから毎回取得して反映**します。既にNotionにある明細でも、Wix側のステータスが変わっていれば同期のたびに更新されるので、Wixで発送済みにマークすればこのアプリ側も追従します。重複登録防止のロジックは移行CLIと同じ（`明細ID`の一意性チェック）なので、何度実行しても安全です。
  - 注文に送料（`priceSummary.shipping`）が含まれる場合、商品明細とは別に `種別=送料` の行を1件追加します（`明細ID`は`{注文番号}_shipping`）。在庫には影響せず、商品別ランキングにも含まれませんが、「取引・在庫履歴」で`種別=送料`で絞り込めば注文ごとの送料額を確認でき、ダッシュボードのKPIカード「送料合計」で累計も確認できます。
  - 注文者の名前（`billingInfo.contactDetails`）も`顧客名`列に自動で記録され、上部ナビの「顧客別集計」タブで、注文（取引ID）ごとに購入商品・送料・合計金額を横並びで確認できます。新しい注文が一番上に表示され、各商品列にはその行での増減（注文は`−`、`入庫`による在庫追加は`+`）と、その時点での残り在庫数（全拠点合計）を表示します。既存の明細に`顧客名`が無い場合は、次回以降の同期で自動的に補完されます（同期結果の「顧客名補完◯件」）。
  - Vercelの無料プラン（Hobby）はCronを**1日1回まで**しか設定できません（それより高頻度にするとデプロイ時にエラーになります）。より高頻度にしたい場合はVercelのProプランへのアップグレードが必要です。日次同期で足りない場合は、下記の手動同期ボタンを使ってください。
- **手動同期**: ACCタブ右上の「今すぐWixと同期」ボタンから、いつでも即座に同期を実行できます。日中に発送状況を反映したい場合や、新しい注文をすぐ取り込みたい場合はこちらを使ってください。
- `WIX_SYNC_SINCE`（未設定時は`SALES_DATA_SINCE`＝2025年3月1日）以降の注文は毎回すべて取得対象になるため、**初回同期で過去分も含めて自動的に取り込まれます**。ただしVercelの関数実行時間には上限（本番は最大60秒）があるため、1回の同期は45秒たった時点でその場で打ち切り、続きは次回の同期に持ち越します（`truncated`が`true`で返ります）。対象期間の注文数が多いほど「今すぐWixと同期」を何度か押す・しばらく待つ必要が増えますが、何度実行しても重複登録はされません。`../migration` のCLIはWixのAPIが使えない場合の代替手段（CSVエクスポートからの移行）として残していますが、通常は不要です。
  - Notionの書き込みは1件あたり約0.35秒間隔にペーシングし、429（レート制限）・5xxは自動的に待機・再試行します（`lib/notion.ts`の`withNotionRetry`）。これにより、大量の新規注文を一度に取り込んだ直後でも他のAPI（売上サマリーや在庫の取得など）が巻き添えで失敗しにくくなっています。
- 本当のリアルタイム性が必要な場合はWixのWebhook（注文作成イベントのpush通知）を使う方式もありますが、今回は署名検証の仕様を確認できなかったため未実装です。必要であれば追って対応します。
- このアプリ全体に認証機能はまだ無く、`/api/acc/sync-wix` もURLを知っていれば誰でも呼び出せます（他の登録系APIも同様）。同期処理自体は明細IDで重複排除されるため誤って何度呼んでもデータは壊れませんが、社内利用に閉じたい場合はVercelのDeployment Protectionなどの導入を検討してください。

### 環境変数（Wix同期用）

| 変数名 | 必須 | 説明 |
| --- | --- | --- |
| `WIX_API_KEY` | ✅ | Wix開発者センターで発行するAPIキー（注文の読み取り権限が必要。`../migration`と共用可） |
| `WIX_SITE_ID` | ✅ | 対象サイトのID |
| `WIX_SYNC_LOCATION` | - | Wix注文を記録する拠点（デフォルト `水上村`） |
| `WIX_SYNC_SINCE` | - | この日付以降の注文のみ同期（デフォルト `SALES_DATA_SINCE`） |

### 重複データのチェック（メンテナンス）

各台帳のダッシュボード最下部に「重複データのチェック」パネルがあります。同じ`明細ID`のページが複数存在していないかを確認し、あれば一番古いものだけを残して残りをNotionの**ゴミ箱に移動**（完全削除ではなく、Notion側でいつでも復元可能）できます。

過去に同期処理の不具合で明細が複数回登録されてしまった場合の復旧用です（原因は修正済みで、今後の同期では発生しません）。データ量が多いと1回の実行では全件を処理しきれないことがあるため、「残り◯グループ」と表示された場合はもう一度実行してください。

## 構成

- `app/api/[ledger]/summary/route.ts` — 月別売上集計・商品別ランキング・KPI（`ledger` は `acc` または `trackteam`）
- `app/api/[ledger]/list/route.ts` — 検索・フィルタ・ページネーション対応の取引一覧
- `app/api/[ledger]/stock/route.ts` — 拠点別の現在庫
- `app/api/[ledger]/stock-in/route.ts` — 在庫登録（POST）
- `app/api/[ledger]/transfer/route.ts` — 拠点間移動の登録（POST、ACC台帳のみ）
- `app/api/[ledger]/manual-entry/route.ts` — 手入力販売・プレゼント・卸し・棚卸調整の登録（POST）
- `app/api/[ledger]/purchase-order/route.ts` — 発注の登録（POST）
- `app/api/[ledger]/purchase-order/receive/route.ts` — 発注に対する納品登録（POST、在庫にも自動反映）
- `app/api/[ledger]/purchase-orders/route.ts` — 発注一覧の取得（GET、ページネーションなし全件）
- `app/api/[ledger]/pending-shipments/route.ts` — 未発送一覧の取得（GET、ページネーションなし全件）
- `app/api/[ledger]/event/status/route.ts` — 取引のステータス変更（POST）
- `app/api/acc/sync-wix/route.ts` — Wix注文の同期（GET: Cron起動用 / POST: 手動同期ボタン用、どちらも同じ処理）
- `app/api/[ledger]/dedupe/route.ts` — 重複明細の確認（GET）・アーカイブ（POST）
- `lib/dedupe.ts` — 重複検出・アーカイブのロジック
- `lib/wix.ts` / `lib/wix-sync.ts` — Wix Orders REST APIクライアントと同期ロジック
- `vercel.json` — Wix同期を定期実行するCron設定
- `app/page.tsx` / `app/track-team/page.tsx` — 各台帳のダッシュボード画面
- `components/dashboard/ledger-dashboard.tsx` — KPIカード・売上推移グラフ・商品別ランキング・現在庫・登録フォーム・取引履歴を組み合わせた画面本体（両台帳で共用）
- `lib/notion.ts` — Notion APIクライアントとクエリ・集計・在庫計算ロジック
- `lib/ledger.ts` — 台帳（acc/trackteam）ごとの拠点・許可操作などの設定
- `components/ui/` — shadcn/ui相当の共通UIコンポーネント（Radix UI + Tailwind CSSで実装）
- `components/dashboard/` — ダッシュボード専用コンポーネント（発注・在庫登録・拠点間移動・手入力記録フォーム、発注一覧・現在庫・取引履歴テーブルを含む）

| 変数名 | 必須 | 説明 |
| --- | --- | --- |
| `NOTION_API_KEY` | ✅ | Notion Internal Integration のトークン（両台帳で共通） |
| `NOTION_DATABASE_ID` | ✅ | アスリートキャリアセンター台帳のデータベースID |
| `TRACK_TEAM_NOTION_DATABASE_ID` | ✅ | 陸上部台帳のデータベースID |

| `SALES_DATA_SINCE` | - | 売上集計の開始日（デフォルト `2025-03-01`）。在庫残高の計算には影響しません |
| `ALLOWED_ORIGIN` | - | APIへのブラウザアクセスを許可するオリジン（カンマ区切りで複数指定可）。未設定時は `*` |
| `WIX_API_KEY` / `WIX_SITE_ID` | ✅（自動同期を使う場合） | Wix注文の自動取り込みに使用。詳細は「Wix注文の自動取り込み」を参照 |
| `WIX_SYNC_LOCATION` / `WIX_SYNC_SINCE` | - | 同上 |

APIキー・データベースIDはサーバーサイド（Route Handlers内）でのみ使用され、クライアントに送信されることはありません。

## Vercelへのデプロイ

1. このリポジトリをVercelにインポート
2. **Root Directory** を `web` に設定（モノレポ構成のため）
3. 上記の環境変数をVercelのプロジェクト設定 → Environment Variables に登録
4. デプロイ

フロントエンドとAPIが同一オリジンで動作するため、通常は `ALLOWED_ORIGIN` の設定は不要です。APIを別ドメイン・別Vercelプロジェクトのフロントエンドから呼び出す場合のみ設定してください。
